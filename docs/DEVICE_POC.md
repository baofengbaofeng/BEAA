# MatePad 11 / HarmonyOS 4 原生与真机验收操作手册

更新：2026-11-06（北京时间）。用途：拿到设备后逐步执行，也可交给远程开发者/代测人员。本文是待执行方法，**不是验收通过报告**。

## 0. 先看当前能做什么

当前原生工程是ArkUI演示骨架：真实跨应用计时/限制、可信休息、家长验证和持久化尚未接入。没有经过实际SDK构建的HAP；当前云环境缺SDK/ohpm/hvigor/hdc。共享业务和浏览器测试通过不代表原生安装或设备管控通过。

因此按以下顺序执行，不跳级：

| 阶段 | 谁执行 | 结束条件 | 缺条件时 |
|---|---|---|---|
| 一、设备信息 | 设备持有人 | 填好型号/系统/电脑信息 | 保留未执行，等设备 |
| 二、工具与连接 | 开发者配合设备持有人 | 匹配IDE识别真实设备 | 标阻塞，不用模拟器冒充 |
| 三、最小权限验证 | 有目标SDK的开发者 | 正式API在目标设备实测计时/限制/恢复 | 给出证据或明确阻塞/No-Go |
| 四、原生接入/构建/安装 | 开发者 | 完整业务接入、真实签名HAP、成功日志 | 不能只交演示骨架就报产品通过 |
| 五、产品与异常验收 | 设备持有人执行、开发者核日志 | 本文P01–P10及补充项有真实证据 | 逐项失败/阻塞，不默认通过 |

复制[验收记录模板](testing/DEVICE_ACCEPTANCE_RECORD_TEMPLATE.md)到自己的测试记录中填写。记录时统一设备时区，保留具体日期/开始结束时间。没有设备时不要填写“通过”。

## 一、拿到设备后：先收集信息（不需要开发工具）

1. 打开平板「设置 → 关于平板/关于设备」，抄录完整硬件型号、系统完整版本/构建号和安全补丁；不要只写“MatePad 11”或“HarmonyOS 4”。菜单名称以实际版本为准。
2. 在电脑查看系统版本，确认有可传输数据的USB线和可用USB接口。没有电脑时，把后续连接/构建步骤交给有工具链的执行方；仅有平板还不能完成本项目的原生构建。
3. 在记录模板填写设备代号如`device-01`。无需向公开记录提供序列号、UDID、真实账号或儿童身份信息；签名若需设备标识，由授权人员在本地保护的环境处理。
4. 记下当前设备日期/时区、屏幕自动休眠设置及系统已有的限时/家长控制配置。测试时明确哪些限制来自BEAA，避免把系统原有家长控制误认为本应用能力。
5. 准备两个可纳管、可恢复的普通测试应用，命名为应用A、应用B；准备秒表与录屏方式。限制测试前由开发者提供可实际执行的解除办法，保留系统设置和必要求助入口。

**本阶段交付**：设备信息表、关于设备页截图（外发前遮盖私人标识）、电脑系统信息。型号或子版本不符合目标时先记录差异，不直接套用本手册的兼容性结论。

## 二、准备匹配工具链并连接设备

### 2.1 开发者准备工具

1. 根据第一阶段的具体设备/系统及电脑系统，核对官方开发者文档中支持的DevEco Studio和SDK版本。当前工程配置的`4.0.0(10)`只是仓库待核对配置，不能据此断言适配目标设备。
2. 从官方渠道安装匹配版本，记录下载来源、IDE/SDK/API、Java、ohpm、hvigor版本。不要为“编过”直接换成较新系统SDK，或把OpenHarmony/模拟器支持等同于目标商业系统支持。
3. 打开仓库`apps/harmony/`，通过该IDE的开发终端同步依赖。SDK/插件不匹配时，以同版本官方Empty Ability/Stage模板对照修复，并记录代码提交；不得跳过真实构建。
4. 本地签名、开发者账号与所需设备授权由有资格的人员配置；账号密码、证书私钥不写进仓库、验收报告或聊天。

仓库工具说明见[原生工程说明](../apps/harmony/README.md)。在**仓库根目录**用Node20+执行以下实际已有脚本，保存输出（与IDE构建自带的Node版本分别记录；不要为运行仓库脚本擅自替换IDE要求的运行时）：

```sh
node scripts/native-preflight.mjs > native-preflight.json
```

若已在IDE确认匹配SDK，但未配置SDK环境绑定，可显式指定其真实目录后重跑：

```sh
node scripts/native-preflight.mjs --sdk "PATH_TO_MATCHED_SDK" > native-preflight.json
```

替换目录占位符，保存为UTF-8文本供复核；脚本只检查目录存在，不核验SDK内容兼容性。紧接着查看退出码：PowerShell执行`$LASTEXITCODE`，Bash/zsh执行`echo $?`。退出2表示缺工具/SDK，退出1为参数错误，退出0仅表示命令和目录可用，**不证明SDK内容兼容、已编译、已签名或已安装**。工具若只在IDE内可用，先在IDE开发终端运行；不要把“终端PATH缺失”和“IDE已构建成功”混为一项结果。

### 2.2 设备持有人配合连接

1. 在平板设置中查找「开发人员选项/开发者选项」。尚未开启时，按该系统版本官方说明操作；常见方式是在「关于平板」连续点击“版本号”直到提示开启。若出现本机解锁验证，只在平板上输入。
2. 按匹配IDE官方连接说明启用所需USB调试选项；用数据线连接电脑，解锁平板，在设备弹出的调试授权中确认当前测试电脑。
3. 在IDE的设备管理窗口找到这台设备，核对型号和系统。设备窗口名称/菜单位置随IDE版本不同，以实际帮助为准。
4. 如匹配SDK附带并支持`hdc`，可在对应开发终端先执行：

```sh
hdc -v
hdc list targets
```

这些是通用连接示例，尚未在本仓库目标设备验证；先用该SDK的帮助确认语法。记录本地目标标识并与IDE设备对应；外发记录用设备代号，不公开唯一标识。旧版工具名称或通道不同时使用该版本官方方法，不把其他调试工具看到设备当成HAP安装成功。

5. 不出现设备时，依次检查数据线能否传输、平板是否解锁、授权弹窗、USB模式、官方驱动/工具版本。不要反复重装应用或清空数据来“修复连接”。

**停止条件**：IDE/官方工具无法识别目标真实设备，记“阻塞”，保存错误和版本；不要继续宣称真机安装或管控已验证。

## 三、先做正式权限可行性验证（开发者执行）

当前项目没有已完成的真实设备适配器。开发者需在匹配SDK中制作最小原生验证程序，使用官方公开能力；设备持有人配合授权与操作。不能直接点击现有“模拟使用/完成休息”来验这一阶段。

### 3.1 先核对正式能力和资格

在模板逐项填写：官方文档链接/访问日期、具体API/权限名称、适用系统/API版本、普通第三方应用是否可申请、是否需要特殊审批/企业或系统身份、实际申请结果。至少分别核对：跨应用统计、限制、解除/恢复、受限后引导答题及重启后的状态查询。

如果只对其他系统版本开放，不推断本机可用；如果只对企业/系统应用开放，不把它当作普通家庭第三方应用已可用。没有官方依据或授权结果时记“未验证/阻塞”。官方明确不支持当前产品形态，或正确实现后仍不能可靠限制/恢复时，附证据判定该形态No-Go；代码尚未接入或编译错误本身不能证明平台No-Go。

### 3.2 做最小真实实验

1. 授权前查询能力，确认没有谎称已启用管控。分别启动测试应用A、B，记录真实状态。
2. 按官方流程申请权限，保存实际结果。确认撤权后的查询也能区分失效，不能用硬编码`supported`或UI开关代替。
3. 用A、B采集跨应用事件，观察息屏、后台和前台播放时的计数口径；写清哪些行为计入有效使用。冻结采样周期、上报延迟及容差，不能测试失败后再扩大容差。
4. 对仅测试应用的范围施加限制，再尝试从桌面/最近任务进入A、B；核对**设备实际上无法继续使用**，而非仅记录接口“成功”。
5. 按已准备的正式解除方法恢复A、B，再核对实际可进入。记录限制和恢复调用、结果与设备状态；解除方法无效则停止后续限制测试，先由开发者解决。
6. 验证受限时能到达学习页面的正式路径，不依赖孩子忽略提示后仍可继续玩。模拟提醒/全屏悬浮窗/模拟点击不能作为系统管控通过证据。

**本阶段交付**：权限/API资格表、最小程序提交与HAP摘要、调用/采集日志、连续录屏、Go/No-Go/未验证结论。未通过这一门槛时可继续独立学习功能，但“全设备强制管控”不能标通过，产品范围调整需另作决定。

## 四、原生业务接入、真实构建与安装

此阶段必须有开发者完成，普通设备持有人不需要自行编写ArkTS。

1. 把共享规则、题库/原题快照、家长验证、使用/学习账本和可信休息接入原生应用，使用第三阶段已验证的适配器。Node `.mjs`及Python参考不是可直接导入ArkTS的原生后端；详见[原生集成说明](development/NATIVE_INTEGRATION.md)。
2. 核对演示按钮已经不能作为真实使用/休息证据，原生设置保存/PIN/持久化有实际实现。尚未实现的功能在记录中写“阻塞/未实现”，不能按演示骨架判完整产品通过。
3. 在匹配IDE中配置授权开发者的本地签名，执行该版本实际可用的构建/`assembleHap`任务。任务名称、参数和产物路径由IDE/模板确认，本文不提供未经验证的一键构建命令。
4. 保存完整构建日志、命令/任务、退出状态、工具链版本、源码提交、HAP路径及SHA256；失败时保留报错，不仅截一张绿色提示。源码提交可用`git rev-parse HEAD`读取，并用`git status --short`核对未提交业务改动；有改动先形成可审查提交或补丁，不将私钥/证书或本地秘密配置纳入。计算包摘要时，替换真实HAP路径，选择电脑支持的命令：

```powershell
Get-FileHash -LiteralPath 'PATH_TO_SIGNED_HAP' -Algorithm SHA256
```

```sh
# macOS
shasum -a 256 "PATH_TO_SIGNED_HAP"
# Linux
sha256sum "PATH_TO_SIGNED_HAP"
```

仅记录实际输出；没有生成包时，本项仍阻塞。
5. 用IDE选择目标设备安装/运行这个**已记录摘要的签名HAP**。如使用支持的hdc，先核对其帮助，再替换示例参数：

```sh
hdc -t DEVICE_ID install "PATH_TO_SIGNED_HAP"
```

`DEVICE_ID`和`PATH_TO_SIGNED_HAP`不是可直接复制的真实值。以上命令仅为匹配工具支持时的示例，不代表当前已有HAP或已实测安装。未识别设备/没有签名包时停在本步。

6. 在平板实际启动，核对安装包/应用版本，进行一次退出后冷启动。当前仓库bundleName为`com.beaa.xuezhishouhu`，如开发者调整，记录实际包名与提交。
7. 保存安装/启动日志和录屏。出现签名/版本不兼容/资源异常时标失败或阻塞，修复后使用新的提交与HAP摘要重新测；不能用另一份包的成功替代。

**设备只装上演示骨架**最多说明该骨架可编译/安装，不说明业务或管控已完成。只有准备好的完整测试包才能进入下面产品用例。

## 五、默认规则的连续测试方法

### 5.1 冻结配置与计时口径

记录：单轮30分钟、每日120分钟、5题/首次答对5题、休息10分钟、年级/学科/知识点、题库摘要和题目ID、设备时区/测试日、采样周期/延迟与事先确认的容差。使用外部设备的独立秒表对照，避免为读秒切离A/B；设备事件和单调时间为实际采集依据。

开发排错可以临时缩短参数，须另记运行ID/配置；不能把加速计时、改系统时钟、模拟按钮或缩短参数的成功当成默认参数验收。默认长时测试需要至少120分钟有效使用、三次各10分钟休息，另加答题和操作时间。

先确认休息采集定义：是否要求连续、如何证明完整区间、息屏/活动/重启如何处理。共享参考按可信完整区间核验，中断/未知不能默认达标；原生未实现相应采集时，休息相关项记阻塞。

### 5.2 P01–P10操作表

每项先填写起始账本revision、日累计、周期累计和实际限制状态。用测试运行ID分隔不同用例；不要在验证持久性/上限的连续流程中重装、清数据或换日来凑通过。

| ID | 具体操作 | 必须观察/保存 | 通过条件与停止条件 |
|---|---|---|---|
| P01 未授权 | 首次运行未授权测试包，查询能力并尝试启动A/B；按官方流程授权后再查询 | 前后权限结果、真实设备状态、录屏 | 未授权/不支持明确显示，不能谎称已管控；无正式权限路径则阻塞/No-Go判定 |
| P02 跨应用采集 | 用秒表连续对照：0–3分钟A，3–6分钟B，6–8分钟息屏，8–10分钟A；非指定息屏段保持亮屏，额外息屏应记录并扣除；记起止计数 | 原始使用事件、屏幕/生命周期事件、计数差、容差 | 按“亮屏前台计入、息屏不计”的口径应约480秒且在事先容差内；若正式API口径不同先明确适用规则，不事后改标准 |
| P03 周期到期 | 在同一周期继续实际使用至30分钟；若已完成P02，应按已累计值继续，而非另清零。到期后从桌面/最近任务打开A/B | 触发时刻、采样/限制调用及系统实际状态 | 可信周期达到阈值触发挑战，A/B实际受限；仅页面提示或模拟到期按钮不通过 |
| P04 学习入口 | 保持受限，从第三阶段确认的正式路径进入答题页；再试继续使用A/B | 入口操作与前后台录屏、限制状态 | 学习页可达，不能绕过它继续使用被管应用；没有实现的系统路径记阻塞 |
| P05 通过但休息不足 | 用已核对答案的固定5题全对，查看待生效资格；在不足10分钟时尝试A/B | 原题ID/首次评分、待休息状态、实际限制 | 尚未满足休息时继续受限。该尝试可能中断连续休息，记录为单独的提前尝试用例 |
| P06 满足休息后恢复 | 从可核验的新连续休息起点开始，按约定条件保持真实10分钟，期间不点按钮自报完成；满足后查看资格并进入A/B | 完整可信休息区间、达标检查点、迁移/恢复调用和设备状态 | 实际休息达标且未到日上限才恢复；不能仅凭墙钟差/两个空闲采样点认定。若检查操作导致已满足的资格被错误清零，记录失败供修复 |
| P07 每日硬上限 | 保留同日累计，按“实际使用30分钟→答题→休息”继续各轮，累计到120分钟；尝试新挑战、旧通过记录/重试和再次打开A/B | 连续账本/事件链、到期状态与实际限制 | 达日上限后不通过答题/旧资格延长；日累计不回退。测试中不要改上限/清数据/跨日；第四轮同时到周期和日上限时日锁优先 |
| P08 后台/息屏/分屏 | 在可使用及受限状态分别切A/B、回桌面、息屏再亮屏；设备允许时进入分屏并旋转 | 起止累计、当前题号/答案、生命周期和限制状态 | 按已确认口径采集，计数/进度不清零；分屏不能绕过限制；未支持功能准确记录 |
| P09 进程终止/重启 | 先记提交快照，在答题中、休息中、日锁后三种场景分别按开发者提供的方法终止测试进程或重启设备，恢复后再查询 | 前后账本/题快照/休息检查点、权限及真实限制、录屏 | 已用时长/题序/首次评分保持，不重复奖励；重启不默认满足休息或清掉日锁；实际设备状态必须重新核对 |
| P10 撤权/卸载失效 | 由持有人在系统设置撤销相关权限，返回应用并尝试A/B；按官方方法恢复测试配置。卸载测试留到数据恢复用例完成后且单独记录 | 撤权事件、告警、真实限制状态、恢复操作 | 准确显示失效，不能继续声称受控；按官方语义核对撤权/卸载后的残留限制并保证持有人可恢复，不能把卸载重装当持久性通过 |

P02为明确口径的测量样例；容差、有效使用定义没有确认时先标待核验。外部系统已有的限时功能应记录并避免混淆，不用它的阻拦来代替BEAA调用证据。

### 5.3 补充功能与异常用例

| 记录ID | 操作与预期 | 状态要求 |
|---|---|---|
| N01 安装/冷启动 | 按第四阶段安装、退出、冷启动；记录包摘要/版本/日志 | 不用浏览器成功代替安装 |
| N02 首次答错 | 一题首次答错，最终首次正确4/5；严格模式不能过，给出讲解；重试不能把原成绩追溯改为5/5 | 题目和原阈值固定，未实现记阻塞 |

## 六、证据保存与提交

每个运行使用独立目录；仓库的`device-logs/`已被Git忽略，原始设备日志先保存在其中，脱敏后再单独提交需要公开的报告。示例：

```text
device-logs/run-001/
  record.md              # 复制验收记录模板填写
  native-preflight.json
  toolchain.txt          # 实际IDE/SDK/工具版本
  source-commit.txt
  build.log
  package-sha256.txt
  install.log
  permission-evidence/  # 官方依据、资格/申请结果
  P02/                  # 起止记录、脱敏事件日志、连续视频
  P03/ ... P10/
  N01/ ... N08/
```

- 日志通过匹配IDE的设备/进程日志窗口或经该工具帮助确认的命令导出；记录过滤条件和起止时间。不要提供未经目标SDK验证的“万能导出命令”。
- 每项关联同一设备/系统、源码提交、HAP摘要、配置、执行步骤、预期/实际和证据文件名。失败要保留失败日志和复现步骤，修复后用新运行ID复测。
- 脱敏后再共享：不含真实PIN/token、账号密码、证书私钥、公开设备唯一标识或可识别儿童身份。保留时间/状态/修订号等诊断信息，避免脱敏后无法关联事件。
- 只保存截图不足以证明跨应用计时/限制，必须有真实采集/调用结果及设备表现的对应证据链。
- 软件规则/管控验收不等于健康改善或教学效果证明；家庭行为试用应另作记录。

## 七、结论怎么填

- **未执行**：尚未实际跑；模板初始值均如此。
- **阻塞**：缺设备/SDK/签名/资格/原生实现/证据，写清负责人和下一步；不能推断支持或不支持。
- **失败**：前置条件满足，实际结果与预期不符；保留日志，修复复测。
- **通过**：该具体设备/版本/提交/包/配置上的用例完整执行，预期与实际一致，有证据可复核。

平台门禁单独写Go/No-Go/未验证：只有正式权限与真实跨应用计时/限制/恢复、受限学习入口满足要求才可Go；No-Go须有官方适用性或正确实现后的实测依据。原生构建、安装、业务、管控分别给结论，不用“编译过”推导“可管控”。所有关键项仍阻塞/未执行时，产品整体仍未验收。

执行结束后：按已验证方法解除测试范围限制，核对A/B和必要系统操作可用，恢复正常时间/休眠等测试改动，关闭不再使用的USB调试/撤销临时电脑调试信任；保留脱敏证据，勿为清理测试而删除需验证的原账本后再报持久性通过。
